# T-ERP — Todorov Tees Business Management System

A real (not mock) ERP/WMS/POS foundation: product & variant catalog, multi-warehouse
inventory with an atomic, race-safe stock engine, role-based permissions enforced at
the database layer, and a dashboard — all backed by a real Postgres database with
Row Level Security, deployed as a static site + managed Postgres backend.

**Status: Phase 1 (foundation) is built and working.** The full spec this project is
based on covers ~76 modules (POS, purchases, price lists, batches/serials, document
templates, import/export, report scheduler, offline sync...). That is a multi-month
build for a real team, not something any single pass can respond to. See
[Roadmap](#roadmap) for exactly what's live today vs. what's next.

---

## 1. Architecture

The original spec calls for a Node.js/Express/PostgreSQL backend. This repo instead
uses **GitHub Pages + Supabase**, because that's the hosting the project is
targeting (`github.com/todorovtees/t-erp` + the Supabase project at
`nkbpbbumyriecvhjykho.supabase.co`). GitHub Pages only serves static files — it
cannot run an Express server — so the roles map like this:

| Spec's ask | This repo |
|---|---|
| Express REST API | [PostgREST](https://postgrest.org), auto-generated by Supabase from the schema, called via `supabase-js` |
| Business logic / transactions | Postgres `plpgsql` functions (`apply_stock_movement`, `complete_sale`) — see §6 below |
| Auth (sessions, bcrypt, etc.) | Supabase Auth (handles hashing, sessions, JWTs) |
| Authorization / permission checks | Postgres Row Level Security policies + a `has_permission()` helper, not middleware |
| "Server" for custom logic (PDF, email/SMS, fiscal devices) | Supabase Edge Functions (Deno) — scaffolded for, not yet built; see `.env.example` |

This is a legitimate production pattern, not a shortcut: the database itself *is*
the API boundary, and every table is deny-by-default until a policy explicitly
opens it. Nothing here is `localStorage`, mock data, or client-side-only auth —
every button that writes data goes through Postgres, through RLS, into real tables.

### Why no `backend/` folder

The spec's folder tree has a `backend/` with `routes/controllers/services/models`.
That doesn't apply here — there is no Node server. If you outgrow what
Postgres functions + Edge Functions can do (e.g. you want a persistent
long-running Node process, or the team is more comfortable with Express), you can
still add a conventional `backend/` later and point it at the same Supabase
Postgres instance (via `DATABASE_URL`) or in front of it. The schema and RLS
policies don't assume GitHub Pages is the only possible client.

## 3. Setup

### 3.1 Run the database migrations

In the Supabase dashboard → **SQL Editor**, run the eight files in
`supabase/migrations/` **in numeric order** (0001 → 0008), each as its own query.
(Equivalently, with the [Supabase CLI](https://supabase.com/docs/guides/cli):
`supabase link --project-ref nkbpbbumyriecvhjykho` then `supabase db push`.)

### 3.2 Connect the frontend to your Supabase project

Open `frontend/js/lib/supabaseClient.js` and paste your **anon/public** key
(Supabase dashboard → Project Settings → API):

```js
export const SUPABASE_ANON_KEY = 'paste-it-here';
```

This key is safe to commit — it has no power on its own; RLS is what protects
the data. Never put the `service_role` key anywhere under `frontend/`.

### 3.3 Load demo data (optional but recommended)

Run `seed/seed_demo.sql` once in the SQL editor. It creates a demo company,
4 warehouses, 3 products with color/size variants and starting stock, plus a
couple of demo customers/suppliers. It's kept out of `migrations/` on purpose —
it's dev data, not schema, and never runs automatically.

### 3.4 Create your first login user

Supabase Auth manages `auth.users` itself (password hashing, sessions) — you
can't `INSERT` into it directly. Create your first user either via
**Supabase dashboard → Authentication → Add user**, or by letting someone sign
up (sign-up UI isn't built yet — add a user from the dashboard for now).

Then link that user to the company and give it a role by running once in the
SQL editor (replace the two values):

```sql
insert into app_users (id, company_id, full_name, username, role)
values (
  '<paste-the-new-user-uuid-here>',
  (select id from companies where eik = 'DEMO-EIK'), -- or your real company
  'Your Name',
  'yourusername',
  'admin'
);
```

Until this row exists, the dashboard will log the user in but show a
"profile not linked" notice instead of data — that's expected, not a bug.

### 3.5 Run it locally

The pages use ES module `<script type="module">` imports, which browsers block
under `file://`. Serve the folder over HTTP:

```bash
npx serve frontend
# or: cd frontend && python3 -m http.server 8080
```

## 4. Deployment (GitHub Pages)

`.github/workflows/deploy-pages.yml` publishes `frontend/` to GitHub Pages on
every push to `main` (GitHub Pages' plain "deploy from branch" mode can only
serve the repo root or `/docs`, not `/frontend`, so this repo uses the Actions
deployment method instead).

One-time setup in the repo:

1. **Settings → Pages → Build and deployment → Source**: select **GitHub
   Actions**.
2. **Settings → Pages → Custom domain**: enter `t-erp.todorovtees.com` and save
   (the `frontend/CNAME` file also ships this on every deploy, so it should
   persist even across a full re-deploy).
3. Once the DNS check passes, enable **Enforce HTTPS**.

Your DNS is already pointed correctly for this:

```
CNAME   t-erp   todorovtees.github.io.   (1 hour TTL)
```

That resolves `t-erp.todorovtees.com` → your Pages site. Propagation plus the
GitHub certificate issuance can take anywhere from a few minutes to a few hours.

## 5. Security model

- **Every table has RLS enabled.** No policy = no access, for every role
  (including `anon`). Read policies scope everything to the caller's own
  `company_id`.
- **Permission checks live in the database**, via `has_permission(module,
  level)`, not in frontend JavaScript — so a user can't grant themselves
  access by editing client code. Default role→permission matrix is in
  migration `0003` (`role_permissions` table), matching the roles/permissions
  examples in the spec (§38–39): Warehouse Operator, Accountant, etc.
- **Stock and money are never written directly.** `inventory`, `sales`,
  `stock_movements`, and `payments` have no client-facing INSERT/UPDATE
  policy at all — the only way to move stock or record a sale is through
  `apply_stock_movement()` / `complete_sale()`, both `SECURITY DEFINER`
  functions that (a) re-check `has_permission()` and company ownership
  themselves, and (b) row-lock (`SELECT ... FOR UPDATE`) before adjusting
  `on_hand`, which is what makes concurrent POS sales safe — two operators
  selling the last unit at the same instant can't both succeed (spec §47).
- **IDOR protection**: policies filter by `company_id = auth_company_id()`
  (a `SECURITY DEFINER` helper reading the caller's own `app_users` row) —
  changing an ID in a request can't return another company's data, because
  the row-level filter is enforced by Postgres itself, not by application code
  that could be bypassed.
- **Money uses `numeric(18,2)` / `numeric(18,4)`** throughout — never
  floating point (spec §48).

## 6. Roadmap

**Built (Phase 1 + 2):**
Companies · Users/Roles/Permissions · Warehouses · Products & Variants ·
Barcodes · Inventory (multi-warehouse, 4-level stock status) · atomic stock
movements · Dashboard (KPIs, 14-day sales chart, low-stock, top products) ·
**POS** (barcode/SKU search, cart, checkout via `complete_sale()`) ·
**Sales** list (filterable) · **Purchases** (receive-stock flow via
`receive_purchase()`, atomic like `complete_sale()`) · **Customers** /
**Suppliers** (full CRUD) · **Payments** list · **Cash registers** (open/close
sessions) · **Reports** (date-range revenue, by-day chart, by-category
breakdown) · **Users** (role/status management) · **Settings** (company
profile) · Login/session handling · GitHub Pages deploy pipeline.

**Not yet built** (grouped roughly by spec section):

- **Batches, serial numbers, expiration tracking** (§9–11)
- **Warehouse transfers, inventory count, returns** (§8, §60–61)
- **Price lists & individual customer pricing** (§14–18) — schema not yet
  added; currently every sale uses `product.sale_price` / `variant.sale_price`
- **Document templates / PDF generation / thermal receipts** (§30–31) — will
  need an Edge Function, since PDF rendering isn't a SQL-expressible task
- **Import/export (CSV/XLSX/JSON)** (§32)
- **Report scheduler** (§63)
- **Creating new login users from the UI** — Supabase Auth's admin API needs
  the `service_role` key, which must never live in the frontend; new users
  are created via the Supabase dashboard (see Users page) or a future Edge
  Function
- **Notifications (in-app/email/SMS)** (§41–42) — needs an Edge Function
- **PWA / offline queue** (§44–45)
- **Fiscal device abstraction layer** (§24)

None of this is blocked architecturally — it's the same pattern as what's
already built (a table + RLS policies + a page that queries it, or a
`SECURITY DEFINER` RPC for anything that needs atomicity). Tell me which
module to build next and I'll continue in the same style.
